How the AutoNgoaLong bot perceives, decides and acts

The bot drives the Flash game Ngọa Long inside the Coowon browser without taking over the mouse. Every tick it captures the window in the background, finds the 1000×600 game canvas, recognises UI parts and reads the screen stack and its numbers into one Snapshot, lets the running feature's rules pick one action, sends it, and checks on the next ticks that the game answered as expected. No OCR, no fixed script, every wait bounded, every tick stoppable.

6 game features + AutoClick 69 UI parts 19 colour probes 15 number fields 35 screens 37 navigation edges 0 OCR calls capture PrintWindow · input PostMessage
Big picture

Layers, one direction of dependency

The UI only talks to the engine; features only see a Snapshot and return actions; perception only sees a 1000×600 canvas; the core never imports the engine. Game knowledge (parts, probes, screens, navigation, templates) lives in profiles/ngoalongviet/ and can be edited without rebuilding. Click any module for its job and files.

Life cycle

From double-click to a saved run

Startup builds one AppServices object that wires everything together. Pressing Bắt đầu builds a fresh Actor for the run and hands the feature to a worker thread, where the decision loop ticks until the goal, a Stop or a failure. Step through the stages.

    TaskRunner · RunControl

    Run states: Start, Pause, Stop

    Each game window has its own TaskRunner, a QThread with four states. Stop and Pause are two threading.Event flags in RunControl. The loop checks them at every tick and before every input (and before each cycle of a click burst), so a Stop takes effect in a few hundredths of a second. Try the buttons.

    Hotkeys: Ctrl+Alt+F10 stops every runner, the pause hotkey toggles all of them, Ctrl+Alt+D toggles debug mode. Bare F-keys are refused.

    Signals the UI receives

    Signals are emitted from the worker thread and Qt queues them onto the UI thread, so the window never freezes during a run. The status signal carries the screen stack of each new Snapshot.

    engine/loop.py · Loop.tick()

    Decide: one action per tick, in a fixed order

    The loop asks, in this order, until something answers. The first answer is the tick's decision; it is logged to run.log once per change, with the values the rules read. Pick a situation to see who answers.

    
      
    
      
    
        
    
          
    Rules
    
          
    Rule(name, on=screen, when=..., do=...). A rule fires when its on screen is the top of the stack and when holds; when and do get that screen's readers (s.chests, s.qty, s.ok...). A reader that is not there, or a Click on a part that is not on the frame, means "does not apply": rules never click blind.
    
        
    
        
    
          
    Navigation
    
          
    nav.yaml is the screen graph: city → chest.wheel by clicking the part icon.tinh_tu (revealing the top icon rows first when hidden), world_map → vkt.lobby at the pagoda's point, any dialog closed by its ✕. Navigator.step() closes what is in the way and takes the first edge of the shortest path; the next tick re-plans from what it sees.
    
        
    
      
    
    
    

    
    
    
      
    engine/actions.py · engine/actor.py · engine/recovery.py
    
      
    Act, then verify
    
      
    Every action that touches the game says what it expects on the next Snapshots and how long that may take: a screen (expect="confirm.ok_cancel"), a predicate (expect=lambda n: n.value("chest.buy", "qty") == 200) or a reader that must change (change=...). While it waits, interrupts may still act; when it is met, its then updates the feature's memory; when it is late, the recovery ladder takes over.
    

      
    
        
    The recovery ladder
    
        
    One rung per trouble (an unmet expectation, 40 idle ticks, a wait past its patience, the same decision 8 times on the same screen). A rule whose expectation is met resets it to 0. A Text whose box reads the wrong value is first typed again (twice, on the same screen) before the ladder is used. Press the button to climb.
    
        
    
        
    
        
    
      
    

      
    
        
    
          
    Watchdogs
    
          
      
            
    • Frozen client: no pixel changed for 30 s while 3+ inputs were sent → the run fails with "game không phản hồi … tải lại trình duyệt (F5)".
      • 
            
    • Covered window: the canvas has not changed for 3 s and the game window is fully hidden (visible_fraction() == 0) → one warning to uncover it.
      • 
            
    • No canvas: no reliable canvas for 20 s → fail.
      • 
            
    • Max run time: the feature's max_minutes ends the run with its summary.
      • 
          
    
        
    
        
    
          
    Actions
    
          
      
            
    • Click(at): one click; the game's mouse then rests at canvas (600, 2), so the clicked button stops glowing.
      • 
            
    • Burst(points, times, interval): a blind run of clicks (the Tinh Tú toggle, ~20 chests/s), verified once afterwards.
      • 
            
    • Text(text, at): double-click, End, Backspaces, the text (digits as key presses), Deletes, Enter.
      • 
            
    • Key(vk), Wait(s, patience=), Navigate(screen), Done(msg), Fail(msg).
      • 
          
    
        
    
      
    

      
    
        
    From a canvas point to a Windows message
    
        
    Rules click points of the 1000×600 canvas (a part's centre, a reader's point, or a fixed spot on a map). Actor.click() turns them into client pixels with the tick's canvas fix: origin + point × scale. Page zoom only changes scale.
    
        
    
          
          
          
          
          
          
        
    
        
    
        
    
        
    Win32InputDriver posts these messages to the top-level Chrome_WidgetWin_1 window. Coowon has no render-widget child, so client coordinates go straight to the browser window and the real cursor never moves.

    engine/runner.py · engine/scheduler.py
    
      
    How a run ends, and what happens next
    
      
    execute(task, actor) never raises. It calls task.run(actor) (for a feature: the decision loop), maps the outcome to a RunResult, and always calls task.on_stop(actor).
    
      
    
        
    DONE
    The feature's goal() returned its summary, a rule returned Done, or the max run time ran out. The summary becomes the log line “Xong: …”.
    
        
    STOPPED
    Cancelled (user pressed Stop) or TaskStopped (the bot chose to stop, for example a declined gold-cost question).
    
        
    FAILED
    LoopFailed (the ladder ran out, a frozen client, no canvas, a rule's Fail), WindowGoneError… The last frame, drawn with its Snapshot, is saved as a failure PNG and the Snapshot is dumped to run.log.
    
      
    
      
    
        
    
          
    After every run
    
          
      
            
    • RunResult carries status, message, duration, counters (clicks, chests, floors, rounds, progress…) and the failure screenshot.
      • 
            
    • The run history stores it under data/ (“Lịch sử” tab).
      • 
            
    • The notifier sends tray, Telegram or Discord messages, with a screenshot cropped to the canvas.
      • 
            
    • logs/run-<id>/run.log keeps one line per decision, every recovery, and the event frames a feature kept (event-NN-*.png); step PNGs in debug mode.
      • 
          
    
        
    
        
    
          
    Routines (“Chuỗi tác vụ”)
    
          
    A routine is a saved list of feature steps with times of day and weekdays, stored in data/routines.json. SchedulerService ticks every 15 s; a missed slot still runs within a 5-minute grace window.
    
          
      
            
    • FAILED step: retried up to retries times after retry_delay_s; then skipped, or the routine ends if stop_on_error.
      • 
            
    • STOPPED step: the whole routine stops.
      • 
            
    • Steps that loop until Stop (Võ Khôi Tháp, AutoClick with 0 rounds) need max_duration_s; when it runs out the step counts as done.
      • 
            
    • Since every feature navigates to its own entry screen, steps need no screen in between. Steps of removed features are switched off at start.
      •

    debug/ · tools/ · selftest.py
    
      
    Debugging and checking without the game
    
      
    
        
    
          
    One DebugFrame, three outputs
    
          
    Each tick's Snapshot becomes a DebugFrame: the parts found (green), the ✕ no screen claimed (red), the screen stack as the status line, the planned clicks. It is drawn by:
    
          
      
            
    • Live overlay: a click-through, top-most Qt window glued over the game; between runs it refreshes from fresh captures.
      • 
            
    • Debug panel in the app, so it works while the game is covered.
      • 
            
    • PNG files logs/run-<id>/NNN-<step>.png in debug mode; a failure frame is saved in every mode.
      • 
          
    
          
    Switch on with --debug, the checkbox, or Ctrl+Alt+D. “Kiểm tra” shows the Snapshot of one capture on the status line.
    
        
    
        
    
          
    Corpus, benchmark, self-test
    
          
      
            
    • python -m ngoalong.tools.explore shot|click|key captures the live canvas into corpus/live/NNN-name.png; labels.yaml gives each frame its expected stack and values (PNGs stay local, labels are in git).
      • 
            
    • tools/perceive.py --bench: every labelled frame perceived and compared (stack, readers, timing, no OCR). 539 frames, all right.
      • 
            
    • --selftest runs the same benchmark on 57 frames bundled into the build, plus the profile, the seven features, the Win32 driver and the main window offscreen; it says SKIP when no corpus is bundled.
      • 
            
    • python -m ngoalong.tools.run_feature <id> --set k=v --stop-after S runs one feature through the app's runner with the run log on the console.

    Extension points
    
      
    Adding a feature
    
      
    
        
      
          
    1. Capture the screens with tools/explore.py (navigation only first), and label each frame in corpus/live/labels.yaml: base, dialogs, overlays, the values a reader must return.
      2. 
          
    2. Cut the parts you need (titles, buttons, icons) in part_crops.yaml, run tools/cut_templates.py, give each a search region in parts.yaml; check them with tools/part_report.py. Colours go in probes.yaml, numbers in numbers.yaml.
      3. 
          
    3. Declare the screens in screens/<area>.yaml (require, forbid, over, close, read) and the ways in and out in nav.yaml. Run --bench until every frame reads right.
      4. 
          
    4. Write features/<feature>.py: @register, Params, entry, Memory, rules(), goal(). Every action names what it expects; never a blind offset next to a costly button.
      5. 
          
    5. Run it live with tools/run_feature.py from several start screens, and with a dialog open; read run.log for recoveries.
      6. 
        
    

    @register
class QuayRuong(Feature):
    id, title, order = "quay_ruong", "Quay Tinh Tú", 20
    Params = QuayRuongParams
    entry = "chest.wheel"        # the loop navigates here

    class Memory(BaseModel):
        opened: int = 0

    def rules(self) -> list[Rule]:
        return [Rule("mở", on="chest.wheel",
                     when=lambda s: s.chests > 0,
                     do=lambda s: Click(s.spin, label="quay",
                                       change=lambda n: n.value("chest.wheel", "chests")))]

    def goal(self, snap) -> str | None:
        return "Hết rương" if snap.value("chest.wheel", "chests") == 0 else None
